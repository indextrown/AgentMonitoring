# AgentMonitoring 사용 예시

Swift 데모 앱을 AgentMonitoring에 연결하고, 자연어 작업을 실제 iPhone Simulator 검증으로 바꾸는 전체 과정을 따라가요. Xcode 실행 설정과 검증 JSON을 먼저 작성할 필요는 없어요. AgentMonitoring이 프로젝트를 감지하고, Codex가 작업별 검증 시나리오를 제안해요.

이 문서에는 일곱 가지 예시가 있어요. 앞의 세 예시는 저장소에 포함된 데모 앱과 실제 실행 캡처로 전체 과정을 따라가요. 뒤의 네 예시는 자신의 앱에 옮겨 쓸 수 있는 응용 레시피예요. 입력 검증, Debug fixture, SwiftUI와 UIKit 화면 구현을 각각 설명해요.

예시 1~4와 6~7에서는 사람이 작업별 검증 조건을 먼저 승인해요. 예시 5에서는 사람이 저장소의 고정 프로젝트 계약을 직접 관리해요. 두 방식 모두 Implementer가 검증 조건을 바꾸지 못하는 상태에서 구현과 검증을 진행해요.

| 예시 | 작업 | 확인할 수 있는 것 |
| --- | --- | --- |
| 1. 식별자 수정 | 완료 카드에 `completion-card` 추가 | 기존 기능을 안전하게 고치고 회귀를 검증하는 흐름 |
| 2. 화면과 기능 구현 | 메시지와 완료 상태를 보여주는 결과 화면 추가 | 새 UI, 화면 전환, 상태 전달을 구현하고 실제 동작을 검증하는 흐름 |
| 3. 실제 앱 기능 구현 | 장보기 항목 추가와 구매 완료 기능 구현 | 입력, 목록 상태, 사용자 조작이 연결된 기능을 처음부터 만들고 검증하는 흐름 |
| 4. 잘못된 입력 처리 | 짧은 닉네임을 거부하고 오류 안내 표시 | 성공 경로는 단위 테스트로, 실패 경로는 실제 화면으로 나눠 검증하는 흐름 |
| 5. 오류 상태 복구 | 데이터 로딩 실패를 fixture로 만들고 재시도 | 만들기 어려운 앱 상태를 재현하고 UI와 내부 상태를 함께 검증하는 흐름 |
| 6. SwiftUI 화면 구현 | 빈 즐겨찾기 화면과 첫 카드 추가 | 상태가 바뀌면 화면이 다시 그려지는 선언형 UI를 구현하고 검증하는 흐름 |
| 7. UIKit 화면 구현 | 이용 안내 화면과 동의 완료 상태 추가 | `UIViewController`, Auto Layout과 target-action으로 UI를 구현하고 검증하는 흐름 |

예시 1~3의 소스는 [`docs/demo-swift-project`](./demo-swift-project/)에서 확인할 수 있어요. 예시 4~7의 identifier와 상태 이름은 설명을 위한 값이에요. 자신의 앱에 적용할 때 실제 화면과 상태 구조에 맞게 바꾸세요.

## 먼저 전체 흐름 이해하기

일반적인 Swift 앱 작업은 다음 순서로 진행해요.

```text
Git 프로젝트 연결
  → Xcode 프로젝트·Workspace와 Scheme 자동 감지
  → 검증 명령 확인
  → 자연어로 작업 목표 작성
  → Codex가 Simulator 조작과 합격 조건 제안
  → 사람이 식별자·입력값·예상 결과 검토
  → 검증 조건 승인과 작업 등록
  → 구현·테스트·Simulator 검증·자가 수정
  → 실행 증거와 변경 내역 최종 확인
```

승인한 검증 조건은 작업에 복사본으로 저장돼요. Implementer가 제품 코드를 수정할 수는 있지만, 같은 작업의 합격 조건을 낮추거나 바꿀 수는 없어요.

`.agentmonitor/project.json`은 필수가 아니에요. 팀 전체가 같은 고정 계약을 공유하거나 Debug state·fixture 같은 고급 기능을 연결할 때만 사용하세요.

## 준비할 것

- `pnpm dev`로 실행한 AgentMonitoring Electron 앱
- ChatGPT 로그인을 마친 AgentMonitoring 계정
- Git으로 관리하는 SwiftUI 앱
- Xcode와 부팅 가능한 iPhone 또는 iPad Simulator
- 저장소에서 통과하는 검증 명령. 이 예시에서는 생성된 Xcode 프로젝트를 `xcodebuild`로 검증해요.

## 예시 1. 빠진 접근성 식별자 수정하기

첫 번째 예시의 목표는 완료 카드에 빠진 `completion-card` 접근성 식별자를 추가하고, 프로젝트 테스트와 Simulator 검증을 모두 통과시키는 거예요.

데모 앱에는 텍스트 입력칸, **검증 시작** 버튼, 버튼을 누른 뒤 나타나는 완료 카드가 있어요. 입력칸과 버튼에는 각각 `demo-message`, `start-verification` 식별자가 있지만, 완료 카드에는 처음부터 `completion-card`를 넣지 않았어요. Codex가 이 누락을 찾아 수정하는 과정을 확인하기 위해서예요.

### 1. Git 프로젝트 연결하기

AgentMonitoring 왼쪽 아래의 **실제 Git 프로젝트 추가**를 누르고 저장소 루트를 선택해요. 연결 직후에는 브랜치, 추적 파일과 Swift 구성을 검사해요. 추적 중인 `.xcworkspace` 또는 `.xcodeproj`가 있으면 실행 대상과 Scheme도 자동으로 찾아요.

![Swift 데모 프로젝트를 AgentMonitoring에 연결한 화면](./images/usage/01-project-connected.png)

프로젝트 설정의 **iOS Simulator 실행 설정**에서 자동 감지한 Xcode 파일과 Scheme을 확인하세요. 기본 실행 기기는 iPhone이에요. iPad에서 검증하려면 실행 기기를 **iPad**로 바꾸고 설정을 저장하세요.

### 2. 검증 명령 설정하기

검증 명령이 비어 있으면 감지된 후보를 선택하거나 **직접 설정**을 눌러 입력해요. 먼저 터미널에서 `xcrun simctl list devices available`을 실행해 사용할 Simulator UDID를 확인하세요. 이 예시에서는 다음 형식의 명령을 저장했어요.

```text
xcodebuild -project AgentMonitoringDemo.xcodeproj -scheme AgentMonitoringDemo -configuration Debug -destination id=<SIMULATOR_UDID> test
```

준비가 끝나면 Code, Build, Run, Observe, Act가 **지금 사용 가능**으로 표시돼요. 검증 명령을 저장하면 Verify도 사용할 수 있어요.

![검증 명령과 AI 접근 계약이 준비된 화면](./images/usage/02-project-ready.png)

기존 캡처를 만들 때는 `tuist test`를 먼저 등록했어요. 하지만 AgentMonitoring이 만든 Git worktree에서는 저장소 루트의 `.git`이 디렉터리가 아니라 파일이라 Tuist가 프로젝트 루트를 찾지 못했어요. 그래서 최종 실행에서는 위의 `xcodebuild` 명령처럼 생성된 Xcode 프로젝트를 직접 지정했어요.

여기에서 꼭 확인할 항목은 다음과 같아요.

- Git 상태가 작업을 시작할 수 있는 상태인지 확인해요.
- 검증 명령이 로컬에서 실제로 통과하는지 확인해요.
- Build와 Run에 올바른 Scheme과 기기 종류가 표시되는지 확인해요.
- 화면과 접근성 트리를 수집하고 identifier 기반 UI 조작을 사용할 수 있는지 확인해요.

### 3. 작업 목표와 완료 조건 쓰기

**첫 작업 만들기** 또는 **새 작업**을 누르고 사람이 확인할 수 있는 결과를 중심으로 작성해요. 이 예시에서는 다음 내용을 사용했어요.

- 작업 제목: `완료 카드 접근성 식별자 추가`
- 목표와 완료 조건: `검증 버튼을 누른 뒤 나타나는 완료 카드에 accessibility identifier "completion-card"를 지정하세요. 기존 단위 테스트와 AgentMonitoring의 Simulator 검증이 모두 통과해야 합니다.`
- 최대 자가 수정 횟수: `3`

![완료 조건을 입력한 새 에이전트 작업 화면](./images/usage/03-task-form.png)

“버튼을 수정해 주세요”처럼 구현 방법만 적기보다, 어떤 동작 뒤에 어떤 상태가 보여야 하고 무엇이 통과해야 하는지 적는 편이 좋아요. 그래야 Test Designer와 Reviewer가 같은 기준으로 결과를 판단할 수 있어요.

### 4. 검증 시나리오 검토하고 승인하기

**Simulator에서 실제 사용 흐름 검증**을 켠 상태에서 **검증 시나리오 만들기**를 눌러요. Codex가 저장소와 작업 목표를 읽고 사용자 조작과 합격 조건을 제안해요.

이 예시에서는 다음 내용이 필요해요.

- `demo-message`에 예시 메시지를 입력해요.
- `start-verification`을 눌러요.
- `completion-card`가 화면의 접근성 트리에 나타나는지 확인해요.
- 최종 화면, 접근성 트리와 UI 조작 결과를 증거로 남겨요.

기존 화면 요소는 코드에 있는 accessibility identifier와 같은지 확인하세요. 새로 만들 요소는 Codex가 제안한 identifier를 그대로 쓸지 사람이 결정해요. 입력값과 예상 결과도 실제 사용 흐름에 맞게 고칠 수 있어요.

검토를 마치면 **검증 조건 승인하고 작업 등록**을 눌러요. 이 시점의 조건이 작업에 고정돼요. 제목이나 목표를 다시 고치면 기존 제안은 사라지므로 시나리오를 다시 만들어야 해요.

### 5. 에이전트 실행 과정 확인하기

작업을 등록한 뒤 상세 화면에서 **실행**을 눌러요. AgentMonitoring은 원본 checkout을 직접 수정하지 않고 별도 worktree와 `agentmonitor/*` 브랜치를 만들어요.

![격리된 worktree에서 Test Designer가 실행되는 화면](./images/usage/04-task-running.png)

실시간 로그에서 다음 순서를 확인할 수 있어요.

1. Test Designer가 요구사항을 검증할 테스트를 만들어요.
2. Critic이 테스트가 성공·실패·경계 조건을 충분히 다루는지 검토해요.
3. Implementer가 제품 코드를 수정해요.
4. Test Runner가 프로젝트 검증 명령을 실행해요.
5. Swift Runtime이 앱을 빌드하고 Simulator에서 조작·관찰해요.
6. 실패하면 수집한 로그와 증거를 다음 Implementer 시도에 전달해요.
7. 모두 통과하면 Reviewer가 변경 내역을 최종 검토해요.

### 6. Simulator에서 실제 동작 확인하기

프로젝트 테스트가 통과하면 AgentMonitoring이 작업에 고정된 실행 설정으로 기기를 부팅하고 앱을 설치해요. 이어서 `demo-message`에 텍스트를 입력하고 `start-verification` 버튼을 눌러요.

![AgentMonitoring이 텍스트 입력과 버튼 탭을 마친 iPhone Simulator](./images/usage/05-simulator-result.png)

화면에 입력한 메시지와 완료 카드가 함께 보이면 UI 조작은 끝난 거예요. AgentMonitoring은 같은 시점의 화면 PNG와 접근성 트리를 저장하고, `completion-card`가 정확히 하나 존재하는지 판정해요.

### 7. 실행 보고서와 변경 내역 검토하기

작업 상세 화면의 실행 보고서에서 시도별 결과를 확인해요. 화면, 접근성 트리, UI 조작 결과, runtime 판정은 같은 실행 ID와 시도 번호로 묶여요.

![프로젝트 테스트와 runtime assertion이 통과한 실행 보고서](./images/usage/06-runtime-report.png)

최종 승인 전에는 다음을 확인하세요.

- 프로젝트 검증 명령이 통과했는지 확인해요.
- `completion-card` 접근성 assertion이 통과했는지 확인해요.
- 화면 증거가 기대한 최종 상태인지 확인해요.
- 변경 파일과 Git patch가 작업 범위를 벗어나지 않았는지 확인해요.
- Reviewer finding이 남아 있지 않은지 확인해요.

결과가 맞으면 **원본에 적용**을 눌러 현재 로컬 브랜치에 반영해요. 이 단계는 자동 merge가 아니라 사람의 최종 승인 단계예요. 결과를 사용하지 않으려면 worktree를 폐기하면 원본 저장소는 바뀌지 않아요.

## 예시 2. 검증 결과 화면 구현하기

두 번째 예시는 기존 코드를 조금 고치는 데서 끝나지 않아요. Codex가 새 SwiftUI 화면, 화면을 여는 버튼, 입력 메시지 전달과 닫기 동작을 함께 구현해요. AgentMonitoring은 완성된 화면으로 직접 이동하고, 화면 구조와 상태가 요구사항에 맞는지 확인해요.

완성할 기능은 다음과 같아요.

1. 사용자가 메시지를 입력하고 검증을 시작해요.
2. 검증이 끝나면 **결과 보기** 버튼이 나타나요.
3. 버튼을 누르면 별도의 **검증 결과** 화면이 열려요.
4. 결과 화면에는 입력한 메시지와 `검증 완료` 상태가 보여요.
5. 사용자는 결과 화면을 닫고 이전 화면으로 돌아갈 수 있어요.

### 1. 구현할 결과를 작업 목표로 작성하기

**새 작업**을 누르고 아래 작업 계약을 입력해요. 구현 방법보다 사용자가 경험할 동작과 검증 가능한 완료 조건을 구체적으로 적는 것이 중요해요.

```text
검증을 완료한 사용자가 별도의 결과 화면에서 입력 메시지와 완료 상태를 확인할 수 있게 구현하세요.

완료 조건:
- 기존 demo-message 입력과 start-verification 버튼 동작을 유지합니다.
- 검증 완료 후 완료 카드 아래에 “결과 보기” 버튼을 표시하고 accessibility identifier를 open-result로 지정합니다.
- 결과 보기 버튼을 누르면 별도의 SwiftUI 화면을 엽니다. 결과 화면의 최상위 요소에는 result-screen 식별자를 지정합니다.
- 결과 화면에 제목 “검증 결과”, 사용자가 입력한 메시지, 상태 “검증 완료”를 표시합니다. 메시지는 result-message, 상태는 result-status 식별자를 사용합니다.
- 결과 화면을 닫을 수 있는 조작 요소에는 close-result 식별자를 지정합니다.
- 상태 전환과 메시지 보존을 기존 단위 테스트 또는 새 단위 테스트로 검증합니다.
- 기존 xcodebuild 테스트와 AgentMonitoring의 Simulator 검증이 모두 통과해야 합니다.
```

![새 결과 화면의 동작과 완료 조건을 입력한 작업 화면](./images/usage/feature/02-task-form.png)

### 2. 새 화면 검증 시나리오 승인하기

작업 목표를 입력한 뒤 **검증 시나리오 만들기**를 눌러요. Codex의 제안에서 다음 흐름을 확인하세요.

1. `demo-message`에 `새 화면 구현이 완료됐어요`를 입력해요.
2. `start-verification`을 눌러 검증을 완료해요.
3. 새로 구현할 `open-result`를 눌러 결과 화면으로 이동해요.
4. `result-screen`, `result-message`, `result-status`가 접근성 트리에 존재하는지 확인해요.
5. 최종 화면, 접근성 트리와 UI 조작 결과를 증거로 저장해요.

Codex가 제안한 이름이 다르면 작업 목표와 맞게 identifier를 직접 고쳐요. 새 요소의 identifier는 아직 코드에 없어도 괜찮아요. 승인한 이름이 Implementer가 제품 코드에 추가해야 할 기준이 돼요.

검토가 끝나면 **검증 조건 승인하고 작업 등록**을 눌러요.

### 3. 테스트와 구현 과정 확인하기

작업을 실행하면 Test Designer가 결과 화면 상태, 메시지 보존과 닫기 동작을 먼저 테스트로 표현해요. Critic이 테스트 범위를 검토한 뒤 Implementer가 화면과 상태 전환을 구현해요.

![Test Designer가 새 화면의 완료 조건을 테스트로 만드는 화면](./images/usage/feature/03-task-running.png)

단순한 UI 모양만 만드는 작업이 아니에요. 프로젝트 테스트는 상태 전환을 확인하고, 승인한 검증 시나리오는 실제 사용자가 거치는 화면 흐름을 확인해요. 둘 중 하나라도 실패하면 AgentMonitoring은 해당 증거를 다음 구현 시도에 전달해요.

### 4. 새 화면의 실제 동작 확인하기

프로젝트 테스트가 통과하면 AgentMonitoring이 iPhone Simulator에서 세 번의 UI 조작을 순서대로 실행해요. 마지막에는 Codex가 새로 만든 결과 화면이 열리고, 처음 입력한 메시지와 완료 상태가 함께 보여야 해요.

![AgentMonitoring이 새로 구현한 검증 결과 화면](./images/usage/feature/04-simulator-result.png)

이 화면은 코드 스냅샷이 아니에요. 격리 worktree의 앱을 빌드하고 Simulator에 설치한 뒤, AgentMonitoring이 텍스트 입력과 버튼 탭을 끝낸 실제 실행 결과예요.

### 5. 기능 전체가 통과했는지 검토하기

실행 보고서에서 프로젝트 테스트와 runtime acceptance를 함께 확인해요. UI 조작 3단계가 모두 성공하고, 결과 화면·메시지·완료 상태와 세 종류의 실행 증거가 모두 확인되어야 해요.

![새 화면 구현과 runtime acceptance가 통과한 실행 보고서](./images/usage/feature/05-runtime-report.png)

실제 실행에서는 첫 번째 구현 시도에서 프로젝트 테스트가 통과했어요. AgentMonitoring은 iPhone 16 Pro Max에서 UI 조작 3단계를 완료하고 접근성 요소 23개를 수집했으며, runtime acceptance 6개를 모두 통과시켰어요.

최종 승인 전에는 다음을 확인하세요.

- 새 화면이 작업 계약에 적힌 정보만 명확하게 보여주는지 확인해요.
- 입력한 메시지가 결과 화면까지 유지되는지 확인해요.
- 결과 화면을 열고 닫는 동작이 기존 검증 흐름을 깨뜨리지 않는지 확인해요.
- 프로젝트 테스트와 runtime assertion이 모두 통과했는지 확인해요.
- 작업 상세의 승인 조건과 최종 실행 결과가 같은지 확인해요.

두 번째 예시는 사용자가 경험할 새 화면을 완료 조건으로 정의하고, 테스트와 실제 화면을 함께 사용해 구현을 검증하는 방법을 보여줘요.

## 예시 3. 장보기 목록 기능 구현하기

세 번째 예시는 실제 앱에서 쉽게 만날 수 있는 장보기 목록을 만들어요. Codex는 빈 화면에 모양만 그리는 것이 아니라 항목 입력, 목록 추가, 구매 완료 상태와 단위 테스트를 함께 구현해요. AgentMonitoring은 완성된 앱에 `우유`를 입력하고 버튼을 눌러 실제 사용 흐름이 이어지는지 확인해요.

완성할 기능은 다음과 같아요.

1. 사용자가 살 항목을 입력해요.
2. **추가**를 누르면 목록에 새 항목이 나타나요.
3. 공백만 입력하면 목록에 추가하지 않아요.
4. **구매 완료**를 누르면 항목이 완료 상태로 바뀌어요.
5. 단위 테스트와 Simulator 실행 결과가 모두 통과해야 해요.

### 1. 사용자가 할 일을 작업 목표로 작성하기

**새 작업**을 누르고 아래 작업 계약을 입력해요. “장보기 화면을 만들어 주세요”에서 끝내지 않고, 입력과 상태 변화가 언제 일어나야 하는지까지 적어요.

```text
누구나 사용할 수 있는 장보기 목록 화면을 구현하세요.

완료 조건:
- 기존 데모 화면을 “장보기 목록” 화면으로 바꾸고 최상위 요소에 accessibility identifier shopping-list-screen을 지정합니다.
- “살 항목을 입력하세요” 입력창을 만들고 shopping-item-input 식별자를 지정합니다.
- “추가” 버튼을 만들고 add-shopping-item 식별자를 지정합니다.
- 사용자가 항목을 입력하고 추가하면 목록에 새 행이 나타나며 입력창은 비워집니다. 공백만 입력한 항목은 추가하지 않습니다.
- 목록 행에는 shopping-item-row, 항목 이름에는 shopping-item-name 식별자를 지정합니다.
- 각 항목에 “구매 완료” 조작 요소를 제공하고 shopping-item-toggle 식별자를 지정합니다.
- 구매 완료를 누르면 항목이 완료된 모습으로 바뀌고 shopping-item-completed 식별자를 가진 완료 상태가 나타납니다.
- 항목 추가, 빈 입력 거부, 구매 완료 상태 전환을 단위 테스트로 검증합니다.
- 기존 xcodebuild 테스트와 AgentMonitoring의 Simulator 검증이 모두 통과해야 합니다.
```

![장보기 목록의 입력과 상태 변화를 완료 조건으로 작성한 화면](./images/usage/shopping/02-task-form.jpeg)

### 2. 장보기 사용 흐름 승인하기

**검증 시나리오 만들기**를 누르고 다음 조작과 합격 조건이 포함됐는지 확인해요.

1. `shopping-item-input`에 `우유`를 입력해요.
2. `add-shopping-item`을 눌러 목록에 추가해요.
3. `shopping-item-toggle`을 눌러 구매 완료로 바꿔요.
4. `shopping-list-screen`, `shopping-item-row`, `shopping-item-name`, `shopping-item-completed`가 접근성 트리에 나타나는지 확인해요.
5. 최종 화면, 접근성 트리와 UI 조작 결과를 증거로 저장해요.

입력값을 다른 품목으로 바꿔도 돼요. 다만 목표에 적은 동작, 제안된 identifier와 합격 조건이 서로 같은 의미를 가리켜야 해요. 검토를 마치면 **검증 조건 승인하고 작업 등록**을 눌러요.

### 3. 테스트가 기능의 빈틈을 찾는지 확인하기

Test Designer는 항목 추가와 완료 전환뿐 아니라 공백 입력도 검사해요. Critic은 공백을 거부한 뒤 입력창 값을 유지할지 비울지 정책이 빠졌다고 지적했어요. Implementer는 공백 입력을 그대로 유지하는 정책을 정하고 테스트에 반영했어요.

![Test Designer가 장보기 목록의 상태 변화를 테스트로 만드는 화면](./images/usage/shopping/03-task-running.jpeg)

이 과정에서 화면 요구사항은 승인한 검증 시나리오가 확인하고, 상태 변화와 예외 처리는 단위 테스트가 확인해요. 한쪽만 통과해서는 승인 단계로 넘어가지 않아요.

### 4. Simulator에서 장보기 기능 사용하기

프로젝트 테스트가 통과하면 AgentMonitoring이 iPhone Simulator에서 `우유`를 입력해요. 이어서 **추가**와 **구매 완료**를 차례로 눌러요. 마지막 화면에는 `우유` 항목과 완료 상태가 함께 보여야 해요.

![우유를 추가하고 구매 완료로 바꾼 실제 장보기 목록 화면](./images/usage/shopping/04-simulator-result.png)

이 화면은 미리 만든 목업이 아니에요. 격리 worktree에서 Codex가 구현한 앱을 빌드하고, AgentMonitoring이 세 번의 UI 조작을 수행한 실제 결과예요.

### 5. 기능 구현 결과 검토하기

실행 보고서에서 프로젝트 테스트와 runtime acceptance를 함께 확인해요. UI 조작 3단계가 성공하고 화면, 항목 이름, 목록 행과 완료 상태가 모두 확인되어야 해요.

![장보기 기능과 runtime acceptance 7개가 통과한 실행 보고서](./images/usage/shopping/05-runtime-report.jpeg)

실제 실행에서는 첫 번째 구현 시도에서 프로젝트 테스트가 통과했어요. AgentMonitoring은 iPhone 16 Pro Max에서 UI 조작 3단계를 완료하고 접근성 요소 113개를 수집했으며, runtime acceptance 7개를 모두 통과시켰어요.

최종 승인 전에는 다음을 확인하세요.

- 입력한 `우유`가 목록에 한 번만 추가됐는지 확인해요.
- 입력창이 비워지고 다음 항목을 받을 수 있는지 확인해요.
- 구매 완료 상태가 글자와 아이콘으로 구분되는지 확인해요.
- 공백 입력과 존재하지 않는 항목 같은 예외 조건을 단위 테스트가 다루는지 확인해요.
- 작업 상세의 승인 조건과 최종 실행 결과가 같은지 확인해요.

첫 번째 예시는 작은 결함을 안전하게 수정하는 흐름을 보여줘요. 두 번째 예시는 화면 전환과 상태 전달을 구현해요. 세 번째 예시는 사용자가 직접 입력하고 상태를 바꾸는 앱 기능 전체를 구현하고 검증해요.

## 예시 4. 잘못된 입력과 오류 안내 검증하기

네 번째 예시는 프로필의 닉네임 입력 규칙을 구현해요. 정상 입력뿐 아니라 사용자가 잘못 입력했을 때 보게 되는 안내까지 검증해요.

완성할 기능은 다음과 같아요.

1. 사용자가 닉네임을 입력해요.
2. 닉네임이 두 글자보다 짧으면 저장하지 않아요.
3. 입력창 아래에 구체적인 오류 안내를 표시해요.
4. 올바른 닉네임은 저장할 수 있어요.

이 예시는 별도의 `.agentmonitor/project.json` 없이 작업별 검증 시나리오를 만들어 진행할 수 있어요.

### 1. 정상 동작과 실패 동작을 함께 작성하기

**새 작업**을 누르고 다음 작업 계약을 입력해요.

```text
프로필 화면에서 닉네임을 수정할 수 있게 구현하세요.

완료 조건:
- 프로필 화면의 최상위 요소에는 profile-form 식별자를 지정합니다.
- 닉네임 입력창에는 nickname-input 식별자를 지정합니다.
- 저장 버튼에는 save-profile 식별자를 지정합니다.
- 닉네임 앞뒤의 공백을 제거한 값이 두 글자보다 짧으면 저장하지 않습니다.
- 잘못된 입력에는 “닉네임은 2자 이상 입력해 주세요.”를 표시하고 nickname-error 식별자를 지정합니다.
- 올바른 닉네임은 저장하고 오류 안내를 제거합니다.
- 한 글자, 공백만 있는 값, 올바른 값의 저장 결과를 단위 테스트로 검증합니다.
- 프로젝트 테스트와 AgentMonitoring의 Simulator 검증이 모두 통과해야 합니다.
```

작업 목표에는 성공 경로와 실패 경로를 모두 적어요. Simulator에서는 한 번의 대표 사용 흐름을 검증하고, 단위 테스트는 입력값의 경계를 더 넓게 확인해요.

### 2. 사용자가 보게 될 실패 경로 승인하기

**검증 시나리오 만들기**를 누르고 다음 동작과 합격 조건이 포함됐는지 확인해요.

1. `nickname-input`에 한 글자 닉네임 `김`을 입력해요.
2. `save-profile`을 눌러요.
3. `profile-form`과 `nickname-error`가 접근성 트리에 남아 있는지 확인해요.
4. `nickname-error`의 label이 `닉네임은 2자 이상 입력해 주세요.`와 같은지 확인해요.
5. 최종 화면, 접근성 트리와 UI 조작 결과를 증거로 저장해요.

오류 요소가 존재하는지만 확인하면 다른 오류 문구가 표시되어도 통과할 수 있어요. 사용자가 정확한 해결 방법을 알 수 있어야 한다면 `label`까지 합격 조건으로 고정하세요.

검토를 마치면 **검증 조건 승인하고 작업 등록**을 눌러요.

### 3. 테스트와 실제 화면이 맡는 범위 확인하기

작업을 실행하면 Test Designer가 닉네임 규칙을 단위 테스트로 만들어요. Critic은 다음 경계 조건이 빠지지 않았는지 확인해요.

- 한 글자 입력은 실패해요.
- 공백만 입력해도 실패해요.
- 앞뒤 공백을 제거한 뒤 길이를 판정해요.
- 두 글자 이상이면 저장해요.
- 올바른 값을 다시 입력하면 이전 오류가 사라져요.

프로젝트 테스트가 통과하면 AgentMonitoring이 Simulator에서 `김`을 입력하고 저장 버튼을 눌러요. 단위 테스트가 상태 규칙을 확인하고, Simulator 검증이 사용자가 실제로 오류 안내를 볼 수 있는지 확인해요.

### 4. 최종 결과 확인하기

승인 전에는 다음 항목을 확인하세요.

- 입력한 닉네임이 저장되지 않았는지 확인해요.
- 입력창 가까이에 오류 안내가 보이는지 확인해요.
- 화면 증거의 문구와 접근성 label이 같은지 확인해요.
- 올바른 입력과 경계값을 단위 테스트가 다루는지 확인해요.
- 구현이 다른 프로필 동작을 깨뜨리지 않았는지 Reviewer finding을 확인해요.

이 예시는 “버튼을 누를 수 있다”보다 “잘못 눌렀을 때 사용자가 문제를 이해할 수 있다”까지 완료 조건으로 만드는 방법을 보여줘요.

## 예시 5. 로딩 실패를 재현하고 복구하기

다섯 번째 예시는 프로필을 불러오지 못한 상태를 Debug fixture로 만들어요. 사용자가 **다시 시도**를 누르면 화면과 앱 내부 상태가 모두 정상으로 돌아오는지 확인해요.

네트워크 장애처럼 매번 같은 시점에 만들기 어려운 상태는 UI 조작만으로 재현하기 힘들어요. Debug fixture를 사용하면 앱이 테스트용 실패 상태를 직접 적용해 같은 조건을 반복해서 검증할 수 있어요.

이 예시는 고급 기능이에요. 앱에 [Swift Debug bridge](../resources/swift-debug-bridge/README.md)를 연결하고 `.agentmonitor/project.json`을 직접 관리해야 해요. Debug bridge는 Debug 빌드에서만 동작해요.

이 예시에서는 작업별 자동 생성 시나리오가 아니라 `.agentmonitor/project.json`의 고정 시나리오를 사용해요. 새 작업 화면에서 **Simulator에서 실제 사용 흐름 검증**을 끄고 작업을 등록하세요. 작업에 별도 승인본이 없으면 AgentMonitoring이 프로젝트 계약의 fixture, UI 조작과 상태 assertion을 사용해요.

### 1. 복구 동작을 작업 목표로 작성하기

**새 작업**에서 다음 작업 계약을 사용해요.

```text
프로필을 불러오지 못했을 때 사용자가 다시 시도할 수 있게 구현하세요.

완료 조건:
- 로딩 실패 화면에는 profile-load-error 식별자를 지정합니다.
- 다시 시도 버튼에는 retry-profile-load 식별자를 지정합니다.
- 다시 시도에 성공하면 오류 안내를 제거하고 profile-screen을 표시합니다.
- 불러온 이름에는 profile-name 식별자를 지정합니다.
- 앱 내부 profile.status는 loaded가 되고 profile.retryCount는 1 증가해야 합니다.
- 최초 실패, 재시도 성공, 연속 실패를 단위 테스트로 검증합니다.
- 프로젝트 테스트와 AgentMonitoring의 Simulator 검증이 모두 통과해야 합니다.
```

화면에서 확인할 결과와 내부 상태에서 확인할 결과를 나눠 적어요. 사용자는 정상 프로필 화면을 확인하고, AgentMonitoring은 Debug state로 실제 복구 상태를 확인해요.

### 2. 실패 상태를 만드는 프로젝트 계약 추가하기

`.agentmonitor/project.json`에서 Debug state와 fixture를 활성화하고, `profile-load-failure` fixture를 선언해요. 아래 예제의 `YourApp.xcodeproj`와 `YourApp`을 실제 Xcode 파일과 Scheme으로 바꾸세요.

```json
{
  "version": 1,
  "adapter": {
    "kind": "ios-simulator",
    "container": "YourApp.xcodeproj",
    "scheme": "YourApp",
    "configuration": "Debug",
    "deviceFamily": "iphone"
  },
  "capabilities": {
    "build": true,
    "run": true,
    "observe": ["screen", "accessibility", "state"],
    "act": ["ui", "fixture"],
    "verify": ["test-command", "runtime-scenario"]
  },
  "debugBridge": {
    "protocol": "file-v1",
    "responseTimeoutSeconds": 10
  },
  "runtimeScenario": {
    "fixture": {
      "id": "profile-load-failure",
      "payload": {
        "retryWillSucceed": true
      }
    },
    "actions": [
      {
        "kind": "tap",
        "identifier": "retry-profile-load",
        "timeoutSeconds": 10
      }
    ],
    "assertions": [
      {
        "kind": "accessibility",
        "name": "프로필 화면 표시",
        "identifier": "profile-screen",
        "property": "exists",
        "expected": true
      },
      {
        "kind": "accessibility",
        "name": "프로필 이름 표시",
        "identifier": "profile-name",
        "property": "exists",
        "expected": true
      },
      {
        "kind": "state",
        "name": "프로필 로딩 복구",
        "path": ["profile", "status"],
        "operator": "equals",
        "expected": "loaded"
      },
      {
        "kind": "state",
        "name": "재시도 횟수 증가",
        "path": ["profile", "retryCount"],
        "operator": "equals",
        "expected": 1
      },
      {
        "kind": "evidence",
        "name": "fixture 적용 결과 저장",
        "target": "fixture"
      },
      {
        "kind": "evidence",
        "name": "최종 앱 상태 저장",
        "target": "state"
      }
    ]
  }
}
```

화면과 접근성만 사용하는 기본 구조는 데모 프로젝트의 [`project.json`](./demo-swift-project/.agentmonitor/project.json)에서 확인하세요.

앱의 `fixtureApplier`는 `profile-load-failure`를 받으면 실패 화면을 표시하고, 다음 재시도는 성공하도록 테스트 상태를 준비해야 해요. `stateProvider`는 최소한 다음 상태를 반환해야 해요.

| 상태 경로 | fixture 적용 직후 | 다시 시도 성공 후 |
| --- | --- | --- |
| `profile.status` | `failed` | `loaded` |
| `profile.retryCount` | `0` | `1` |

프로덕션 사용자 데이터나 인증 토큰은 fixture payload와 Debug state에 넣지 마세요.

### 3. fixture, UI 조작과 상태 판정 순서 이해하기

프로젝트 계약을 사용하는 작업에서는 다음 순서로 검증해요.

```text
앱 실행
  → profile-load-failure fixture 적용
  → 실패 화면과 다시 시도 버튼 표시
  → retry-profile-load 탭
  → 최종 화면과 접근성 트리 수집
  → Debug state 수집
  → 화면 요소와 profile 상태 판정
```

fixture는 앱을 실행한 뒤 UI 조작보다 먼저 적용돼요. 따라서 `retry-profile-load`는 fixture가 만든 실패 화면에 실제로 보여야 해요. identifier가 없거나 둘 이상이면 안전을 위해 조작을 중단해요.

### 4. 복구 결과와 증거 확인하기

실행 보고서에서 같은 시도의 증거를 함께 확인하세요.

- fixture 증거에 `profile-load-failure`가 적용됐는지 확인해요.
- UI 조작 증거에서 `retry-profile-load` 탭이 성공했는지 확인해요.
- 최종 화면에 오류 대신 프로필 이름이 보이는지 확인해요.
- 접근성 트리에 `profile-screen`과 `profile-name`이 있는지 확인해요.
- Debug state의 `profile.status`가 `loaded`인지 확인해요.
- `profile.retryCount`가 `1`인지 확인해요.

이 예시는 화면만으로 구분하기 어려운 복구 상태를 fixture로 재현하고, UI 증거와 앱 내부 상태를 하나의 승인 기준으로 묶는 방법을 보여줘요.

## 예시 6. SwiftUI로 상태 기반 화면 구현하기

여섯 번째 예시는 SwiftUI로 즐겨찾기 화면을 만들어요. 처음에는 빈 상태를 보여주고, 사용자가 버튼을 누르면 첫 번째 즐겨찾기 카드가 나타나요.

SwiftUI는 상태가 바뀌면 `View`를 다시 계산해 화면을 갱신해요. 이 예시에서는 빈 상태와 카드 상태를 별도 화면 전환 없이 같은 `View`에서 검증해요.

완성할 UI는 다음과 같아요.

1. 즐겨찾기가 없으면 빈 상태 문구와 추가 버튼을 보여줘요.
2. 사용자가 **샘플 즐겨찾기 추가**를 눌러요.
3. 빈 상태가 사라지고 `Cafe Morrow` 카드가 나타나요.
4. 글자 크기를 키워도 제목과 버튼을 읽고 누를 수 있어야 해요.

이 예시는 별도의 `.agentmonitor/project.json` 없이 작업별 검증 시나리오를 만들어 진행할 수 있어요.

### 1. SwiftUI 화면의 결과를 작업 목표로 작성하기

**새 작업**을 누르고 다음 작업 계약을 입력해요.

```text
기존 SwiftUI 앱에 즐겨찾기 화면을 구현하세요.

완료 조건:
- 프로젝트의 기존 NavigationStack과 상태 관리 방식을 유지합니다.
- 화면의 최상위 요소에는 favorites-screen 식별자를 지정합니다.
- 즐겨찾기가 없으면 “아직 즐겨찾기가 없어요” 문구를 표시하고 favorites-empty-state 식별자를 지정합니다.
- “샘플 즐겨찾기 추가” 버튼을 만들고 add-sample-favorite 식별자를 지정합니다.
- 버튼을 누르면 빈 상태를 숨기고 “Cafe Morrow” 카드 하나를 표시합니다.
- 카드에는 favorite-card, 이름에는 favorite-title 식별자를 지정합니다.
- SwiftUI 기본 컴포넌트와 Dynamic Type을 사용하고 고정 높이로 텍스트를 자르지 않습니다.
- 빈 상태와 카드 상태 전환을 단위 테스트로 검증합니다.
- 프로젝트 테스트와 AgentMonitoring의 Simulator 검증이 모두 통과해야 합니다.
```

“예쁘게 만들어 주세요”처럼 주관적인 목표만 적지 마세요. 화면에 있어야 할 정보, 조작 뒤 바뀌는 상태와 접근성 identifier를 함께 적어야 자동 검증 기준을 만들 수 있어요.

### 2. 빈 상태에서 카드 상태로 바뀌는 흐름 승인하기

**검증 시나리오 만들기**를 누르고 다음 조작과 합격 조건을 확인해요.

1. `add-sample-favorite`를 눌러요.
2. `favorites-screen`이 계속 존재하는지 확인해요.
3. `favorite-card`와 `favorite-title`이 나타나는지 확인해요.
4. `favorite-title`의 label이 `Cafe Morrow`인지 확인해요.
5. `favorites-empty-state`가 사라졌는지 확인해요.
6. 최종 화면, 접근성 트리와 UI 조작 결과를 증거로 저장해요.

`exists: false` assertion을 사용하면 새 카드가 나타난 것뿐 아니라 이전 빈 상태가 사라진 것도 확인할 수 있어요.

검토를 마치면 **검증 조건 승인하고 작업 등록**을 눌러요.

### 3. SwiftUI 구현과 테스트 범위 확인하기

작업을 실행하면 Test Designer가 빈 목록과 첫 항목 추가를 상태 전이로 표현해요. Implementer는 기존 앱의 구조를 먼저 확인하고 같은 상태 관리 방식을 따라야 해요. 요청하지 않은 UIKit wrapper나 새 아키텍처를 추가하면 작업 범위를 벗어나요.

코드와 테스트에서는 다음 항목을 확인하세요.

- 하나의 상태가 빈 화면과 카드 화면을 결정하는지 확인해요.
- 버튼이 상태 변경만 요청하고 화면 구조를 직접 조작하지 않는지 확인해요.
- `ForEach`를 사용한다면 항목에 안정적인 식별값이 있는지 확인해요.
- 큰 글자에서도 텍스트가 잘리지 않도록 고정 높이를 피했는지 확인해요.
- 빈 목록과 항목이 있는 목록을 단위 테스트가 모두 다루는지 확인해요.

### 4. 완성된 SwiftUI 화면 확인하기

프로젝트 테스트가 통과하면 AgentMonitoring이 Simulator에서 추가 버튼을 눌러요. 최종 화면에는 `Cafe Morrow` 카드가 보이고 빈 상태는 없어야 해요.

승인 전에는 다음 항목을 확인하세요.

- 카드가 한 번만 추가됐는지 확인해요.
- 카드 제목과 버튼이 화면에서 읽기 쉬운지 확인해요.
- 접근성 트리의 identifier와 label이 승인한 조건과 같은지 확인해요.
- 화면 증거에서 여백, 정렬과 긴 텍스트 잘림을 직접 확인해요.
- Git patch가 기존 SwiftUI 구조를 불필요하게 바꾸지 않았는지 확인해요.

AgentMonitoring은 접근성 트리로 화면 구조와 상태를 판정해요. 색상, 여백과 시각적 균형은 최종 화면 증거를 사람이 확인해야 해요.

## 예시 7. UIKit으로 Auto Layout 화면 구현하기

일곱 번째 예시는 UIKit으로 서비스 이용 안내 화면을 만들어요. `UIViewController`가 화면 계층을 구성하고, Auto Layout이 위치를 정하며, 버튼의 target-action이 동의 완료 상태를 갱신해요.

이 예시는 코드로 UIKit 화면을 구성하는 프로젝트를 가정해요. Storyboard를 사용하는 프로젝트라면 작업 목표에서 기존 Storyboard와 segue 구조를 유지하도록 바꾸세요.

완성할 UI는 다음과 같아요.

1. 제목, 안내 문구와 **동의하기** 버튼을 세로로 배치해요.
2. 사용자가 **동의하기**를 눌러요.
3. 완료 문구가 나타나고 버튼을 다시 누를 수 없게 바뀌어요.
4. 작은 iPhone과 큰 글자에서도 내용이 겹치지 않아야 해요.

### 1. UIKit 구현 방식을 작업 목표에 고정하기

**새 작업**을 누르고 다음 작업 계약을 입력해요.

```text
기존 UIKit 앱에 코드 기반 서비스 이용 안내 화면을 구현하세요.

완료 조건:
- TermsAgreementViewController를 만들고 기존 화면 전환 구조에 연결합니다.
- UIViewController의 최상위 view에는 terms-screen 식별자를 지정합니다.
- 제목 “서비스 이용 안내”를 표시하고 terms-title 식별자를 지정합니다.
- 본문, 여백과 버튼은 UIStackView와 Auto Layout으로 배치하며 safe area를 기준으로 제약을 설정합니다.
- “동의하기” 버튼에는 accept-terms 식별자를 지정합니다.
- 버튼을 누르면 “동의가 완료됐어요.” 문구를 표시하고 accepted-message 식별자를 지정합니다.
- 동의가 끝나면 버튼의 isEnabled를 false로 바꿉니다.
- UILabel과 UIButton은 Dynamic Type을 지원하고 여러 줄 본문을 자르지 않습니다.
- 동의 전후 상태와 중복 탭 방지를 단위 테스트로 검증합니다.
- 프로젝트 테스트와 AgentMonitoring의 Simulator 검증이 모두 통과해야 합니다.
```

UIKit 프로젝트에서는 Storyboard, 코드 기반 Auto Layout, SnapKit처럼 이미 선택한 UI 구성 방식을 먼저 확인하세요. 예시는 코드 기반 Auto Layout을 요구하므로 Implementer가 다른 방식으로 화면을 새로 만들지 않게 범위를 고정해요.

### 2. target-action 뒤의 화면 상태 승인하기

**검증 시나리오 만들기**를 누르고 다음 조작과 합격 조건을 확인해요.

1. `accept-terms`를 눌러요.
2. `terms-screen`과 `terms-title`이 계속 존재하는지 확인해요.
3. `accepted-message`가 나타나는지 확인해요.
4. `accepted-message`의 label이 `동의가 완료됐어요.`인지 확인해요.
5. `accept-terms`의 enabled 값이 `false`인지 확인해요.
6. 최종 화면, 접근성 트리와 UI 조작 결과를 증거로 저장해요.

UIKit에서는 각 `UIView`의 `accessibilityIdentifier` 속성에 작업 계약의 값을 지정해야 해요. 화면에 보이는 title이나 좌표만으로 대상을 찾지 않아요.

검토를 마치면 **검증 조건 승인하고 작업 등록**을 눌러요.

### 3. UIKit 구현과 테스트 범위 확인하기

작업을 실행하면 Implementer는 뷰 계층을 구성하고 제약을 활성화한 뒤 버튼에 target-action을 연결해요. Test Designer는 동의 전후 상태와 중복 실행을 프로젝트 구조에 맞는 테스트로 만들어요.

코드와 테스트에서는 다음 항목을 확인하세요.

- UI 변경이 main thread에서 일어나는지 확인해요.
- 같은 뷰를 계층에 여러 번 추가하거나 제약을 중복 활성화하지 않는지 확인해요.
- safe area와 readable content guide를 기존 화면 규칙에 맞게 사용하는지 확인해요.
- `numberOfLines`와 Dynamic Type 설정이 긴 안내 문구를 허용하는지 확인해요.
- target-action이 한 번 실행된 뒤 중복 동의를 만들지 않는지 확인해요.

Auto Layout 경고는 화면 PNG만으로 놓치기 쉬워요. 프로젝트 테스트와 실행 로그에 `Unable to simultaneously satisfy constraints`가 없는지도 함께 확인하세요.

### 4. 완성된 UIKit 화면 확인하기

프로젝트 테스트가 통과하면 AgentMonitoring이 Simulator에서 **동의하기**를 눌러요. 완료 문구가 나타나고 같은 버튼은 비활성화되어야 해요.

승인 전에는 다음 항목을 확인하세요.

- 제목, 본문, 버튼과 완료 문구가 자연스러운 순서로 배치됐는지 확인해요.
- 작은 화면에서도 버튼이 가려지지 않는지 확인해요.
- 완료 문구의 label과 버튼의 enabled 값이 승인한 조건과 같은지 확인해요.
- Auto Layout 경고와 중복 target 등록이 없는지 확인해요.
- Git patch가 기존 UIKit 화면 전환 방식을 유지하는지 확인해요.

SwiftUI와 UIKit 중 어떤 방식을 쓰더라도 AgentMonitoring의 검증 원리는 같아요. 사람은 완료 조건을 먼저 고정하고, AgentMonitoring은 identifier로 UI를 조작한 뒤 화면과 접근성 상태를 증거로 남겨요.

두 예시의 Simulator 검증은 선택된 기기 종류에서 한 번의 사용 흐름을 확인해요. 글자 크기 단계와 여러 화면 크기 조합을 자동으로 바꾸지는 않아요. Dynamic Type과 다양한 기기 크기는 별도의 Xcode 테스트나 수동 확인으로 보완하세요.

## 고정된 프로젝트 계약이 필요할 때

일반적인 작업에서는 `.agentmonitor/project.json`을 만들지 않아도 돼요. AgentMonitoring이 Xcode 실행 설정을 내부 데이터베이스에 저장하고, 사람이 승인한 검증 시나리오를 해당 작업에 고정해요. 대상 저장소에는 새 파일이 생기지 않아요.

다음 상황에서는 프로젝트 계약을 직접 관리할 수 있어요.

- 팀이 같은 Xcode container, Scheme과 기기 종류를 Git으로 공유해야 해요.
- Debug state와 fixture처럼 자동 생성 화면에서 지원하지 않는 고급 기능이 필요해요.
- 이미 운영 중인 고정 시나리오를 그대로 유지해야 해요.
- 이전에 기록한 실행을 같은 조건으로 재현해야 해요.

데모 프로젝트의 [기본 계약](./demo-swift-project/.agentmonitor/project.json), [결과 화면 계약](./demo-swift-project/.agentmonitor/examples/feature-screen.json), [장보기 계약](./demo-swift-project/.agentmonitor/examples/shopping-list.json)은 이런 재현용 예시예요.

새 작업에서 사람이 승인한 시나리오가 있으면 그 작업에서는 승인본을 먼저 사용해요. 승인본이 없는 작업은 프로젝트의 `.agentmonitor/project.json`을 사용해요. 프로젝트 계약을 나중에 바꿔도 승인본이 있는 작업의 합격 조건은 바뀌지 않아요.

## 자주 막히는 지점

### 프로젝트가 준비 완료로 바뀌지 않아요

검증 명령이 비어 있는지, 원본 Git checkout에 커밋하지 않은 변경이 있는지 확인하세요. Build와 Run이 보이지 않으면 프로젝트 설정에서 자동 감지된 Xcode container와 Scheme을 확인해요. 자동 감지에 실패했다면 직접 입력하고 **다시 검사**를 누르세요.

프로젝트 계약을 직접 사용하는 경우에만 `.agentmonitor/project.json`의 JSON 문법과 `container`, `scheme` 값을 추가로 확인하세요.

### Simulator를 찾지 못해요

Xcode에서 해당 iOS runtime과 Simulator가 설치되어 있는지 확인하세요. 프로젝트 설정의 실행 기기가 iPhone이면 사용 가능한 iPhone, iPad이면 사용 가능한 iPad를 선택해요.

### UI action이 대상을 찾지 못해요

SwiftUI는 뷰에 `.accessibilityIdentifier(...)`를 적용하고, UIKit은 `UIView.accessibilityIdentifier`에 값을 지정하세요. 같은 identifier가 둘 이상이면 안전을 위해 조작을 중단해요. label이나 화면 좌표 대신 작업 등록 전에 승인한 identifier와 정확히 같은 값을 사용해야 해요.

### 프로젝트 테스트는 통과하지만 runtime이 실패해요

실행 보고서의 화면, 접근성 트리, UI 조작 결과를 같은 시도 번호로 함께 확인하세요. 실패 증거는 다음 자가 수정 시도에도 전달되므로, 최대 시도 횟수 안에서 복구되면 이전 실패와 최종 통과를 모두 비교할 수 있어요.
