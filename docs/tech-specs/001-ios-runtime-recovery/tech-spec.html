iOS Simulator 검증 환경과 자가 복구 개선

요약

AgentMonitoring이 iOS 앱을 검증할 때 필요한 로컬 설정을 격리 작업공간에서도 그대로 사용할 수 있게 하고, 서로 다른 실행 조건을 독립된 시나리오로 검증하도록 바꿔요. 원본 저장소에서 Git으로 제외한 .xcconfig는 작업공간의 같은 경로로 자동 복사해 Codex, 환경 준비, 프로젝트 테스트와 Simulator 빌드가 함께 읽어요. 검증이 실패하면 실제 화면과 접근성 트리를 먼저 수집하고, 환경 문제와 제품 코드 문제를 구분한 뒤 필요한 단계만 다시 실행해요.

이 변경으로 사용자는 Mapbox 토큰 같은 값을 저장소에 커밋하지 않고도 격리 작업공간에서 앱을 실행할 수 있어요. AI는 수정할 수 없는 환경 문제에 구현 횟수를 낭비하지 않고, 제품 코드로 해결할 수 있는 실패에만 자가 수정 루프를 사용해요.

배경

WORK-BEBF4F91 작업은 프로젝트 테스트까지 통과했지만 세 번째 Simulator 조작에서 mapbox-current-location-button을 찾지 못해 실패했어요. 격리 작업공간의 MAPBOX_ACCESS_TOKEN은 비어 있었고, Git에서 제외된 Secrets.xcconfig는 작업공간에 복사되지 않았어요. 앱은 유효한 토큰이 없으면 Mapbox 지도 대신 안내 화면을 표시하므로 해당 버튼을 만들지 않았어요.

당시 앱 실행기는 개인정보 권한은 simctl privacy로 준비했지만 프로젝트별 빌드 설정이나 앱 실행 환경변수를 전달하지 않았어요. 시나리오 생성기는 Mapbox 토큰이 필요하다는 사실을 요약 문장에는 남겼지만 실행 가능한 사전 조건으로 표현하지 못했어요. 이후 실행 환경값 주입은 추가했지만, 환경 준비와 프로젝트 테스트도 원본 프로젝트와 같은 파일을 읽어야 하는 경우에는 기존 Secrets.xcconfig를 직접 사용할 수 없다는 빈틈이 남았어요.

현재 runtime 계약은 하나의 actions 배열과 하나의 assertions 배열만 가져요. 이 구조에 토큰이 있는 상태와 없는 상태, 로딩 중 상태와 완료 상태가 함께 들어가면 한 번의 실행과 한 번의 최종 화면으로는 모든 조건을 만족할 수 없어요.

최대 구현 시도 횟수도 전체 파이프라인에서 공유해요. 해당 작업은 설정 파일 누락과 프로젝트 UI 테스트 실패를 수정하는 데 앞선 두 번을 사용했고, 세 번째 실행에서 처음 발견한 Simulator 실패를 다시 수정할 기회를 얻지 못했어요.

UI 조작기는 요소 탐색에 실패하면 접근성 트리와 화면을 저장하기 전에 테스트를 종료해요. Implementer는 실제로 어떤 화면이 표시됐는지 확인하지 못하고 식별자를 찾지 못했다는 문자열만 받아요.

목표

  • 사용자가 프로젝트별 빌드 설정과 앱 실행 환경값을 AgentMonitoring 화면에서 등록할 수 있어야 해요.
  • 원본 저장소에서 Git으로 제외한 .xcconfig는 작업공간의 같은 상대 경로에서 전체 작업 파이프라인이 읽을 수 있어야 해요.
  • AgentMonitoring 설정에 등록한 민감한 값은 저장소, .agentmonitor/project.json, 작업 계약, 이벤트 로그에 평문으로 남지 않아야 해요.
  • 작업을 실행하기 전에 필수 환경값의 존재를 확인하고, 누락되면 구현 횟수를 사용하지 않은 채 사용자 입력을 기다려야 해요.
  • 서로 다른 권한, 토큰, fixture, 화면 상태를 각각 독립된 Simulator 검증 케이스로 실행해야 해요.
  • 로딩 중처럼 일시적인 상태는 해당 동작 직후의 체크포인트에서 검증해야 해요.
  • UI 조작이 실패해도 실패 시점의 화면, 접근성 트리, 완료된 조작 내역을 증거로 남겨야 해요.
  • 실패를 환경 설정, 검증 계약, 실행 인프라, 제품 코드 문제로 분류해야 해요.
  • 제품 코드로 해결할 수 있는 실패만 Implementer 자가 수정으로 보내야 해요.
  • 기존 version 1 프로젝트와 작업 기록을 읽을 수 있어야 해요.

목표가 아닌 것

  • AgentMonitoring이 Mapbox 같은 외부 서비스의 토큰을 발급하거나 임의의 값을 만들어 주지 않아요.
  • 외부 비밀 저장소나 CI의 secret을 자동으로 동기화하지 않아요.
  • 실제 iPhone과 iPad 장치 실행을 이번 범위에 포함하지 않아요.
  • 앱이 테스트 가능한 상태나 fixture를 제공하지 않는 경우 제품의 실패·timeout 상황을 임의로 조작하지 않아요.
  • 사람이 승인한 검증 조건을 AI가 실패를 피하기 위해 자동으로 삭제하거나 약화하지 않아요.
  • 모든 iOS 시스템 팝업과 외부 SDK 화면을 범용 UI 조작 대상으로 지원하지 않아요.

계획

사용자 흐름

  1. 프로젝트가 Git에서 제외한 .xcconfig를 이미 사용하면 사용자는 원본 저장소에 파일을 그대로 유지해요.
  2. .xcconfig가 없거나 작업마다 다른 값이 필요하면 프로젝트 설정의 실행 환경에서 로컬 값을 등록해요.
  3. 각 항목에는 사람이 알아볼 이름, 주입할 대상 이름, 적용 범위, 민감 정보 여부를 설정해요.
  4. 적용 범위는 Xcode 빌드 설정, Simulator 앱 실행 환경, 또는 둘 다 중 하나를 선택해요.
  5. 작업 등록 화면에서 AI가 검증 시나리오를 만들면 필요한 환경 항목을 별도 사전 조건으로 보여줘요.
  6. 등록된 값이 없으면 설정 필요 상태와 프로젝트 설정으로 이동하는 버튼을 보여줘요.
  7. 사용자는 독립된 검증 케이스와 각 케이스의 실행 조건을 확인한 뒤 승인해요.
  8. 실행 중 실패하면 작업 화면에서 실패한 케이스, 조작 순서, 식별자, 실제 화면, 접근성 트리를 함께 확인해요.
  9. 환경값을 추가한 경우에는 구현 없이 검증만 다시 실행할 수 있어요.

실행 환경 저장과 주입

작업을 시작하거나 다시 실행하면 AgentMonitoring은 원본 저장소에서 Git으로 제외된 .xcconfig를 찾아 격리 worktree의 같은 상대 경로로 복사해요. 원본이 일반 파일이고 1MB 이하인지, 대상 경로가 worktree 밖으로 벗어나지 않는지, worktree에서도 계속 Git 제외 상태인지 확인해요. 심볼릭 링크는 원본과 대상 모두 허용하지 않고 복사본 권한은 소유자만 읽고 쓸 수 있도록 제한해요.

이 복사본은 Codex, 환경 준비 명령, 프로젝트 테스트, Simulator 빌드가 작업 전체에서 함께 사용해요. 재실행할 때 원본 내용으로 갱신하고, 게시 직전에도 Git 제외 상태를 다시 확인해 실수로 커밋되는 것을 막아요. 작업 완료·승인 또는 폐기로 worktree를 정리하면 복사본도 함께 없어져요. 원본 저장소의 파일은 수정하지 않아요.

프로젝트 설정에는 환경 항목의 이름과 적용 범위만 일반 데이터로 저장해요. 민감한 값은 Electron safeStorage로 암호화한 뒤 프로젝트별로 저장해요. macOS에서는 운영체제 Keychain이 암호화 기반을 제공해요.

AgentMonitoring 설정에 직접 등록한 민감한 값은 다음 위치에 저장하지 않아요.

  • Git이 추적하는 저장소 파일
  • .agentmonitor/project.json
  • 작업의 runtime 계약 JSON
  • 이벤트와 오류 로그
  • PR 본문과 runtime 증거

빌드 설정이 필요한 값은 작업 전용 임시 xcconfig에 기록하고 xcodebuild가 그 파일을 읽게 해요. 파일 권한을 제한하고 빌드가 끝나거나 작업을 중단하면 즉시 삭제해요. 명령행 인자와 로그에는 실제 값을 넣지 않아요.

앱 실행 환경값은 simctl launch 프로세스에 SIMCTL_CHILD_ 접두사로 전달해요. 예를 들어 앱이 UITEST_MAPBOX_ACCESS_TOKEN을 읽는다면 실행 프로세스에는 SIMCTL_CHILD_UITEST_MAPBOX_ACCESS_TOKEN을 전달해요.

실행 전 검사는 계약에 적힌 필수 항목과 프로젝트 설정을 대조해요. 값이 없거나 운영체제 보안 저장소를 사용할 수 없으면 Simulator를 실행하지 않고 환경 설정 필요로 멈춰요.

runtime 계약 version 2

version 2 계약은 하나의 평면 시나리오 대신 독립된 케이스 목록을 가져요. 실제 값은 포함하지 않고 필요한 환경 항목의 키만 참조해요.

{
  "version": 2,
  "runtimeScenarios": {
    "cases": [
      {
        "id": "mapbox-current-location-success",
        "name": "Mapbox에서 현재 위치로 이동",
        "preconditions": {
          "permissions": [
            { "service": "location", "state": "granted" }
          ],
          "requiredEnvironmentKeys": ["mapbox-public-token"]
        },
        "steps": [
          {
            "kind": "action",
            "action": { "kind": "tap", "identifier": "Mapbox" }
          },
          {
            "kind": "assert",
            "assertions": [
              {
                "identifier": "mapbox-current-location-button",
                "property": "exists",
                "expected": true
              }
            ]
          }
        ]
      }
    ]
  }
}

성공, 권한 거부, 토큰 누락, 위치 조회 실패, timeout은 각각 다른 케이스로 만들어요. 각 케이스는 필요한 권한과 환경값을 적용한 뒤 앱을 새로 실행해요. 앱 데이터 초기화가 필요한 케이스는 이를 사전 조건에 명시해요.

action과 assert를 실행 순서에 맞는 steps로 표현해요. 이 구조를 사용하면 버튼을 누른 직후의 로딩 상태와 요청 완료 후의 활성 상태를 서로 다른 체크포인트에서 확인할 수 있어요.

계약 승인 전에 다음 모순을 검사해요.

  • 같은 체크포인트에서 같은 속성에 서로 다른 예상값이 있어요.
  • 필수 환경값이 있는 케이스와 없는 케이스의 조건이 섞여 있어요.
  • 최종 화면에서 이미 사라지는 일시 상태를 검사해요.
  • fixture가 필요한 실패 조건인데 프로젝트가 fixture 조작을 지원하지 않아요.
  • 조작보다 앞선 체크포인트가 조작 결과를 기대해요.

모순을 발견하면 AI가 코드를 구현하기 전에 시나리오 수정 화면으로 돌아가요. 수정한 계약은 사용자가 다시 승인해야 해요.

케이스 실행 순서

동일한 빌드 환경을 사용하는 케이스는 앱을 한 번 빌드하고 설치 산출물을 재사용해요. 각 케이스는 아래 순서로 실행해요.

  1. 필수 환경값과 계약의 유효성을 확인해요.
  2. 이전 앱 프로세스를 종료해요.
  3. 케이스가 요구한 권한, 앱 데이터, fixture 상태를 준비해요.
  4. 케이스 전용 앱 실행 환경값을 주입하고 앱을 실행해요.
  5. steps를 순서대로 실행하고 각 체크포인트의 증거를 저장해요.
  6. 케이스 결과를 저장한 뒤 다음 케이스를 독립적으로 시작해요.
  7. 모든 케이스가 통과한 경우에만 Reviewer와 게시 단계로 이동해요.

코드 수정 뒤에는 직전에 실패한 케이스를 먼저 실행해요. 실패한 케이스가 통과하면 전체 케이스를 다시 실행해 회귀를 확인해요.

실패 증거와 오류 분류

UI 요소를 찾지 못하거나 중복 식별자를 발견해도 XCTest를 바로 끝내지 않아요. 실패를 기록한 뒤 아래 증거를 먼저 수집해요.

  • 실패한 케이스와 step 번호
  • 찾으려던 accessibility identifier
  • 실패 전까지 완료된 조작 내역
  • 현재 화면 스크린샷
  • 현재 접근성 트리
  • 실제 화면에서 찾은 identifier와 label 후보

XCTest는 실패 정보를 기계가 읽을 수 있는 marker JSON으로 출력해요. 실행기는 길이가 제한된 Xcode 로그 문자열에만 의존하지 않고 이 결과를 파싱해요. 화면과 접근성 증거는 실패한 실행에도 runtime_evidence로 저장해요.

실행기는 실패를 다음처럼 처리해요.

분류예시처리
환경 설정필수 토큰이나 로컬 설정 누락사용자 입력을 기다리고 구현 횟수를 사용하지 않아요.
검증 계약한 케이스에 상충하는 예상값이 존재시나리오 수정과 재승인을 요구해요.
실행 인프라CoreSimulator 연결 실패제품 코드를 수정하지 않고 재실행 안내를 제공해요.
제품 코드승인된 identifier 누락이나 실제 결과 불일치증거를 Implementer에 전달해 자가 수정해요.

사용자가 정한 최대 구현 시도 횟수는 Implementer가 제품 코드를 수정한 횟수만 세어요. 환경 준비와 계약 수정은 이 횟수를 소비하지 않아요. Simulator 실패가 제품 코드 문제로 판정되어 Implementer가 수정하면 구현 시도 횟수를 하나 사용해요.

기존 계약 호환과 이전

version 1 계약은 읽기 호환성을 유지해요. 기존 permissions, actions, assertions는 하나의 legacy 케이스로 변환해 화면에 보여줘요.

기존 계약을 Simulator에서 다시 실행할 때는 모순 검사를 먼저 수행해요. 문제가 없으면 변환된 계약을 사용할 수 있어요. 상충하는 조건이 있으면 자동 실행하지 않고 version 2 케이스로 분리한 초안을 제안한 뒤 사용자 재승인을 받아요.

기존 작업의 attempt 값은 기록으로 유지해요. 새 작업부터 환경·계약 대기 상태와 구현 시도 횟수를 분리해 저장해요.

다음 동작을 자동 테스트로 확인해요.

  • 암호화한 환경값을 다시 읽을 수 있고 다른 프로젝트에서 조회할 수 없어요.
  • Git에서 제외한 .xcconfig가 같은 worktree 상대 경로로 복사되고 재실행 때 최신 내용으로 갱신돼요.
  • 복사한 .xcconfig가 worktree 변경 내역에 나타나지 않고, Git 제외 규칙이 사라지거나 대상이 심볼릭 링크면 복사와 게시를 거부해요.
  • 작업을 폐기하면 복사한 .xcconfig도 worktree와 함께 삭제돼요.
  • 민감한 값이 로그, 이벤트, 계약 JSON, 임시 파일명에 포함되지 않아요.
  • 작업 완료·실패·중단 뒤 임시 xcconfig가 삭제돼요.
  • 필수 환경값이 없으면 Implementer를 실행하지 않고 사용자 입력 상태가 돼요.
  • version 1 계약이 legacy 케이스로 변환돼요.
  • 상충하는 assertion과 지원하지 않는 fixture 조건을 실행 전에 거부해요.
  • 여러 케이스가 권한과 앱 상태를 공유하지 않고 독립적으로 실행돼요.
  • UI 조작 실패 후에도 화면, 접근성 트리, 조작 내역이 저장돼요.
  • 제품 코드 실패만 자가 수정 횟수를 사용해요.
  • 환경값을 등록한 뒤 구현 없이 다시 검증으로 파이프라인을 이어갈 수 있어요.

Demo iOS 프로젝트에는 토큰이 필요한 정상 경로, 토큰이 없는 경로, 권한 거부 경로를 각각 독립된 케이스로 추가해요. 실제 비밀값은 테스트 fixture와 운영체제 보안 저장소에서만 제공해요.

고려 사항

  • Electron safeStorage를 사용할 수 없는 운영체제 상태에서 민감한 값을 저장하지 않는 정책을 확정해야 해요. 기본 제안은 평문 저장으로 대체하지 않고 설정을 거부하는 방식이에요.
  • 임시 xcconfig가 기존 프로젝트의 xcconfig 우선순위를 바꾸지 않는지 Tuist 프로젝트와 일반 Xcode 프로젝트에서 각각 확인해야 해요.
  • Mapbox처럼 외부 네트워크가 필요한 SDK는 토큰이 유효해도 네트워크 장애로 실패할 수 있어요. 토큰 누락과 네트워크 실패를 다른 오류로 분류해야 해요.
  • 케이스마다 앱 데이터를 초기화하면 정확성은 높아지지만 실행 시간이 늘어날 수 있어요. 기본 초기화 범위와 재사용 조건을 구현 전에 확정해야 해요.
  • 프로젝트 설정에서 하나의 값을 빌드 설정과 앱 실행 환경의 서로 다른 이름에 함께 연결하는 UI가 필요한지 결정해야 해요.
  • 환경값을 삭제하거나 변경했을 때 이미 승인된 계약을 다시 승인해야 하는 범위를 정해야 해요. 값 자체가 아니라 요구 항목의 이름과 적용 범위가 바뀔 때만 재승인하는 방식을 우선 검토해요.
